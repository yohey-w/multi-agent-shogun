# Design Doc Reviewer

基本設計書とDFD図を一貫した品質・フォーマットでレビューし、監査対応として使用可能なレビュー結果を出力するスキル。

## Overview

このスキルは、基本設計書（PDF）とDFD図（PDF）を入力として、以下の3つの観点でレビューを実施し、構造化されたMarkdown形式でレビュー結果を出力する。

## When This Skill Applies

このスキルは以下の場合に適用される：
- 基本設計書のレビュー依頼
- DFD図の品質確認
- 設計書の監査対応チェック
- 設計書の記載項目・記載量の確認

## レビュー観点

### 1. 記載項目として充足しているか

基本設計書として必要な項目が網羅されているかを評価する。

**確認項目:**
| 項目 | 確認内容 |
|------|----------|
| 機能概要・目的 | システムの目的と機能範囲が明記されているか |
| 前提条件・制約 | 利用条件、制約事項が明記されているか |
| 処理概要 | 主要処理の概要が記載されているか |
| 画面仕様 | 画面構成、レイアウトが記載されているか |
| 操作仕様 | ユーザー操作フローが記載されているか |
| 処理仕様 | 処理ロジック、アルゴリズムが記載されているか |
| データ仕様 | テーブル定義、データ項目が記載されているか |
| 権限制御 | アクセス権限の制御方法が記載されているか |
| エラー仕様 | エラーコード、エラー処理が記載されているか |
| 非機能要件 | 性能、可用性等の要件が記載されているか |
| クラス設計 | クラス構成、関連が記載されているか |
| 特記事項 | 補足情報、注意事項が記載されているか |
| QA/FB | 質問・回答の履歴が記載されているか |
| 改訂履歴 | 版数管理、変更履歴が記載されているか |

### 2. 記載量として充足しているか

要件定義から詳細設計への橋渡しとして、適切な粒度・量で記載されているかを評価する。

**確認項目:**
| 観点 | 確認内容 |
|------|----------|
| 基本設計としての粒度 | 「何を実現するか」と「どう実装するか」が分離されているか |
| クラス設計の粒度 | クラス名・主な属性・関連/継承関係が記載されているか |
| 画面別の入力制御 | 必須/形式/相関チェックが記載されているか |
| 詳細設計との役割分担 | 詳細設計との分離が適切か |

### 3. DFD図としてデータの流れが明確か

監査時に「このシステムでは誰がどんなデータを入力し、どう処理され、どこに保存されるか」を図で説明できる状態かを評価する。

**確認項目:**

#### 3-1. 業務とシステム間のデータの流れ
- データを入力する人・部門・システムが図に書かれているか
- データを受け取る人・部門・システムが図に書かれているか
- データの流れが矢印で示されているか

#### 3-2. 各処理に必要なデータ
- 処理への入力データが書かれているか
- 処理が参照するデータベース・マスタが書かれているか
- 処理からの出力データが書かれているか
- データの内容が具体的に書かれているか

#### 3-3. 処理同士のつながり
- 処理の順番が分かるか
- 処理間のデータの受け渡しが矢印で示されているか
- 処理の単位が適切か

#### 3-4. DFD図の読みやすさ・整合性
- 凡例が説明されているか
- 図のレイアウトが整理されているか
- 処理名・データ名が分かりやすいか
- 基本設計書との整合が取れているか

## DFD図の記号

| 記号 | 名称 | 意味 | 例 |
|------|------|------|-----|
| 長方形 | 外部エンティティ | システムの外にいる人・部門・他システム | 「人事部」「従業員」「外部API」 |
| 角丸長方形 | プロセス（処理） | データを変換・加工する処理 | 「入力チェック」「登録処理」 |
| 矢印 | データフロー | データの流れ（矢印の向きが流れる方向） | 「従業員情報」「エラーメッセージ」 |
| 二重線/開いた長方形 | データストア | データベース・ファイルなどの保管場所 | 「従業員マスタ」「ログテーブル」 |

## 評価基準

### 記載項目の評価記号

- **◎**：十分に記載されている（修正不要）
- **○**：概ね記載されている（軽微な補足で完了）
- **△**：一部不足がある（対応が必要）→ 必ず「次のアクション」を記載
- **×**：記載がない/大幅に不足 → 必ず「次のアクション」を記載
- **-**：該当なし

### 総合評価のランク

- **A**：そのまま監査対応資料として使用可能
- **A-**：軽微な修正で監査対応資料として使用可能
- **B+**：若干の修正が必要
- **B**：修正が必要
- **C**：大幅な修正が必要

### 改善提案の優先度

| 優先度 | 基準 |
|--------|------|
| **高** | 監査指摘リスクあり／データの流れが追跡できない／文書間で不整合がある |
| **中** | 読みにくさがある／軽微な記載漏れ／推奨される追記事項 |
| **低** | あれば望ましい程度／見た目の改善 |

## 使用手順

### Step 1: PDFの文字化け確認

DFD PDFを読み込み、文字化けを確認する。

**文字化けの検知方法:**
- 連続する「?」や「□」が多数存在する
- 日本語が期待される箇所に記号のみが表示される
- PDFの一部のみ日本語が表示され、他が文字化けしている

### Step 2: 画像変換（文字化け発生時）

テキスト抽出で文字化けしている場合でも、画像として読み取れる場合はレビュー可能。
画像として読み取れない場合は、pdf_to_images.sh等で画像変換を実施。

```bash
./pdf_to_images.sh "対象ファイル.pdf"
```

### Step 3: レビュー実施

基本設計書PDFとDFD PDFを読み込み、上記のレビュー観点に従ってレビューを実施。

### Step 4: 結果保存

レビュー結果を出力フォーマットに従ってMarkdownファイルとして保存。

## 文書間差異の取り扱いルール

基本設計書と詳細設計書の間で差異が見つかった場合、**どちらが正しいかを判断しない**。

- 差異を発見した場合は「差異がある」という事実のみを指摘する
- 「どちらに寄せるべきか」の判断は文書作成者に委ねる

## Best Practices

- レビュー前に必ず共通プロンプト（レビュー基準）を確認する
- PDFの文字化けは画像読み取りで対応可能な場合がある
- 初版の場合、DFD図・画面遷移図は基本設計書と同時作成扱いのため、改訂履歴への別途記録は不要
- 改善提案には必ず「完了条件」を記載する
- 文書間差異は事実のみ指摘し、判断しない
